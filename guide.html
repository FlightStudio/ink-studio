Ink Studio v2

Build guide

This page is the map. It updates after each plan step. Postgres, the website, the stationery style guide, the page geometry, the letter document, the shared letter page, letter storage, file uploads, and the editor with autosave are ready on your own computer. Formatting from the toolbar is next.

12 of 36 steps in the repository. Step 14 starts the worker in two pools. Step 11 adds the floating toolbar.

On your computer

Prepare the machine, then the database

Do the machine setup once. Then start Postgres and apply the identity tables.

  1. Install Docker Desktop and leave it running. On Linux, Docker Engine plus the Compose plugin is enough. If docker compose says permission denied, open a new terminal after your user is in the docker group, or run the compose commands with sg docker -c '…'.
  2. Install Node.js 22 from nodejs.org.
  3. In a terminal: corepack enable then corepack prepare pnpm@10.33.4 --activate.
  4. Clone this repository and stay on main. After a pull request is merged, git pull brings it in.
  5. pnpm install

Postgres 17 on port 5434

From the repository root, with Docker running:

cp .env.example .env
cp tools/.env.example tools/.env
docker compose up -d
docker compose ps
pnpm db:migrate

docker compose ps should show the postgres service as healthy before you migrate. pnpm db:migrate creates users, organizations, organization_users, letters, and assets. After a git pull that brings a new table, run pnpm db:migrate again; it only applies what is new.

Look at the tables in the browser with Drizzle Studio. It uses the database config already in the repo, so you do not install a second Postgres or a separate database app:

pnpm db:studio

Leave that terminal open while you browse users, organizations, organization_users, and letters. Stop it with Ctrl+C. The connection it uses is:

postgresql://postgres:postgres@127.0.0.1:5434/ink_studio

That password is only for this local database. Do not reuse it anywhere else. Stop the database later with docker compose stop. The data stays in the Compose volume.

The same tables from the terminal:

docker compose exec postgres psql -U postgres -d ink_studio -c '\dt'

Open the website

After migrate succeeds, seed one local user and start Next.js:

cp apps/web/.env.example apps/web/.env.local
pnpm seed
pnpm dev

Open http://127.0.0.1:3000. It goes straight to your letters on the warm desk colour, under the name of your organization, Ink Studio. Health is http://127.0.0.1:3000/api/health and answers {"ok":true}.

The stationery style guide is http://127.0.0.1:3000/styleguide. With the dev server already running, this writes .local/screens/styleguide-1440x900.png and .local/screens/styleguide-ipad.png:

pnpm screens /styleguide

Docker has to be running for the screenshots. The first run downloads the Playwright browser image.

Running pnpm seed again keeps that same user and organization. The password in the connection string is only for this local database.

http://127.0.0.1:3000 and http://localhost:3000 are the same website, and saves work from either. If one of them gives an empty page, use the other.

An iPad on the same network needs DEV_LAN_HOST set to this computer's LAN address in the root .env and in apps/web/.env.local, and NEXT_PUBLIC_PLATFORM_URL=http://<that-address>:3000 in apps/web/.env.local. Restart pnpm dev, then open that address on the iPad. The dev server listens on port 3000 on every interface.

M2. Design system and page model

Done 5. Stationery design system and browser harness

Open /styleguide while pnpm dev is running. One sheet of letter paper lies on a warm desk, the way the editor will look:

  • A small white bar floats over the top edge of the sheet: undo, redo, align left, centre and right, and Library. Hover a button for its name. Undo and redo follow the alignment you pick.
  • The sheet says Start with a blank sheet. That line and the page title, Quiet stationery, are the only places the serif display face appears.
  • Under the sheet: the letter title, Saved, a View menu that switches between On the desk and As printed, and Delete, which asks before it does anything.
  • Library slides in from the right with two tabs, Drawn and From a photo. Photo doodles carry status pills, and Erase opens a small eraser size slider.
  • On the left, the legend: every stationery colour with its name, the four type sizes with real sample text, and the four status pills.

On an iPad the legend moves above the sheet.

The sheet carries the scanned paper from project-post, apps/web/public/images/paper.png, repeated at its own size. As printed drops the texture and shows plain white.

Done 6. Page specs and exclusion floats

The paper the printer takes is now data. There is one entry for the Thanks.io windowless letter, the default, and one for the Thanks.io 6×9 postcard. Each entry has the canvas size, the safe zone, the text margin, how many sides a creator may use, and the corners the printer keeps clear. A new printer or product is one more entry.

  • A letter writes on every side up to its page limit. The default limit is 3 sides, and Thanks.io allows up to 12. The barcode corners of the first side sit inside the margin, so they never push text aside.
  • A postcard has an image front and a writing back. The address and postage block on the back is cut out of the text area, so text flows around it.
  • Text skips the gap between sides, and the postcard's address block, through ordinary CSS floats. Exclusions on the left and the right can overlap and both hold.
  • The same pure functions count the sides in use, measure how far text runs past the last side, and flag a doodle that sits outside the safe zone, over a kept-clear corner, or beyond the last side.

To check this step on your computer:

pnpm --filter @repo/types test
pnpm --filter @repo/render test

Each test is named for what it proves, for example “the band between side 1 and side 2 covers both margins and the gap” and “the postcard's address block shapes the back's text”. Add --reporter=verbose to see every name.

The five ink colours a creator writes with are in the catalogue now: Midnight, Ink blue, Sepia, Forest, and Oxblood. Open /styleguide and the legend has an Ink section. Pick a colour and the sample line under it changes to that ink.

Done 7. One letter document and validation

A letter is now one defined shape: Tiptap JSON with paragraphs, line breaks, and one ink style per run of text (font, size, and colour). Doodles placed on the page live in the same document, so one undo will cover typing and moving a doodle alike. The document also records how many sides the creator added and, for a postcard, the front image.

  • One parser checks every letter against the catalogues. An ink colour, size, font, or alignment that is not in the catalogue is refused, so a saved letter can never carry made-up CSS such as red;background:url(x).
  • Every id must be a UUID. Unknown fields, unknown node types, bold, HTML strings, and future schema versions are refused.
  • A letter is held to 20,000 characters and 200 placed doodles. It may not ask for more sides than its product allows, and only a postcard may have a front image.
  • The Human Seal is worked out from the document. All in Karla's handwriting reads “Written in Karla's own handwriting”. Some of it reads “Partly written in Karla's own handwriting”. Doodles add “doodles hand-drawn”. A letter with nothing human in it has no seal.
  • The merge fields first name and last name are in the catalogue, with sample values for the preview. The @ menu that inserts them comes in step 33.

To check this step on your computer:

pnpm --filter @repo/types test --reporter=verbose
pnpm --filter @repo/render test --reporter=verbose

The seal cases are under humanSeal, and the parser cases read like “an ink colour outside the catalogue is refused”.

Done 8. Shared letter page in Chromium and WebKit

There is now one page component, LetterPage. The editor will show it, the print preview will show it, and the worker will turn it into the proof PDF. Because they all draw the same page with the same CSS, the letter a creator sees is the letter that prints.

  • A letter is drawn as sheets of paper on the desk with a gap between them while editing, and as plain white sheets with no gap when printed. The text column runs down through every side the letter may use.
  • Text skips the gap between sides, so no line is ever cut in half across a page break. On a postcard the text flows around the address and postage block on the back.
  • While editing, the corners the printer keeps clear are hatched, so a creator can see them. They disappear in print.
  • Caveat, Patrick Hand, and Homemade Apple are in the repository with their licences, under packages/render/fonts. The page loads them by id, so the editor and the print use the same font files.
  • A measure reads where every line sits, in inches, even when the page is zoomed. That count decides how many sides a letter uses and how far it runs over.

The tests open seven sample letters in real Chromium and real WebKit, the engine behind Safari on the iPad. Each runs at screen resolution and at print resolution, in both edit and print mode. The two engines agree on the number of sides for every sample. One gap remains: in WebKit, the down arrow from the last line of a side jumps further than the next line when a paragraph carries on past the gap. The editor in steps 10 and 11 will move the caret across that gap itself.

There is no page in the app that shows a letter yet. The editor in step 10 is the first. To run the browser tests yourself, with Docker running:

pnpm --filter @repo/render test --silent=false

The first run downloads the Playwright browser image. The output lists each sample with its line and side counts in both engines, for example nearly-full edit @1.000: chromium 61 lines 3 sides, webkit 61 lines 3 sides.

Checked: pnpm lint, pnpm typecheck, and pnpm test, including all 86 render tests.

M3. Editor

Done 9. Store letters, titles, revisions

A letter now lives in Postgres, in a letters table, so it survives a reload and follows you to another device. Each letter belongs to your organization. There is still no editor screen; step 10 adds it. For now the letter is reached through the website's API, which the editor will call.

  • A new letter is called Untitled letter and starts empty, in Caveat at 20 pt in Ink blue. A new postcard is called Untitled postcard.
  • Every save carries the revision it was based on. If another tab saved in between, the save is refused with “This letter changed in another tab.” and nothing is overwritten. Step 10 shows that message with two choices, Load the latest and Keep mine.
  • Every save is checked by the same parser as in step 7. A colour, size or font outside the catalogue is refused, and so is a title that is empty, over 120 characters, or holds a control character. Spaces around a title are trimmed.
  • Deleting a letter hides it everywhere but keeps the row, with the time it was deleted.
  • Another organization cannot read, save or delete your letters. To them a letter of yours does not exist.

To try it on your computer, after git pull, pnpm install, and pnpm db:migrate, start pnpm dev and in a second terminal create a letter:

curl -s -X POST http://127.0.0.1:3000/api/letters \
  -H 'Origin: http://127.0.0.1:3000' -H 'Content-Type: application/json' -d '{}'

It answers with the new letter's id, for example {"id":"01a17f47-…"}. Open http://127.0.0.1:3000/api/letters/<that id> in the browser to see its title, revision 1, and the empty Caveat letter. It also shows up in pnpm db:studio under letters. A request without the Origin header is refused, so another website cannot save into your letters.

The tests for this step run on their own throwaway Postgres in Docker:

pnpm --filter @repo/db test --reporter=verbose
pnpm --filter @repo/services test --reporter=verbose

The names read like “a stale save is refused and changes nothing” and “another organization cannot read, save or delete the letter”.

Checked: pnpm lint, pnpm typecheck, and pnpm test, including 12 database and 9 letter service tests, and every API answer above against the local database.

Done 10. Write on the page with autosave

The editor is on the page. http://127.0.0.1:3000 opens your letters. With none yet it says Write your first letter, with a button, Start a letter. Afterwards each letter is a small sheet with its title and when it was last edited, and New letter sits top right.

  • A new letter opens on a blank sheet of paper reading Start writing…. Type straight onto the page in Caveat, Ink blue, 20 pt. When the text runs past the first side, a second sheet appears under it and the text carries on there.
  • The title and the save line sit in a small paper pill at the bottom of the screen. Click Untitled letter to rename it; Enter or Escape finishes, and an empty title goes back to the old one.
  • The save line reads Saving… while you type, then Saved a moment after you stop. Without a network it reads Offline, retrying and keeps trying, waiting longer each time, up to thirty seconds. Leaving the page with an unsaved change asks first.
  • Open the same letter in two tabs and write in both. The tab that saves second reads This letter changed in another tab, with Load the latest and Keep mine. Keep mine saves over the other tab's version. A tab with nothing unsaved quietly loads the newer version when you come back to it.
  • The three dots under a letter in the list open Delete, which asks before it removes the letter.
  • The fonts come from the website itself, at /fonts/stock/caveat, so the page never waits on Google Fonts.

To try it on your computer, after git pull and pnpm install, run pnpm dev and open http://127.0.0.1:3000. Letters you made with curl in step 9 are in the list already.

The website now has tests of its own. The save logic runs in pnpm test. Eight journeys drive a real browser against your running pnpm dev, from a Playwright container, with Docker running:

pnpm --filter web test --reporter=verbose
pnpm --filter web test:e2e

The journeys read like “typed text survives a reload”, “the older tab can keep its version”, and “a clean tab reloads a newer version when it comes back into view”. They add letters to your local database as they go.

Checked: pnpm lint, pnpm typecheck, and pnpm test, with all 6 save tests, and all 8 journeys against a dev server, twice.

M4. Files and jobs

Done 13. Upload files, one checked way to read them

Files now have a home. Every photo, doodle mask and font file a creator uploads is stored in Google Cloud Storage and recorded in a new assets table that belongs to their organization. On your computer a stand-in for Cloud Storage runs in Docker next to Postgres, on port 4443, so nothing leaves the machine. There is no upload button yet; the doodle library in step 17 and the photo lift in step 21 add them.

  • A photo may be a JPEG, PNG or WebP up to 15 MB. A doodle mask is a PNG up to 8 MB. A font file is a TTF or OTF up to 4 MB.
  • The type is read from the first bytes of the file, never from its name. A JPEG renamed to .png is still a JPEG.
  • An iPhone HEIC photo is refused with “HEIC photos cannot be uploaded, so choose a JPEG, PNG or WebP.” Anything else outside the list reads “That kind of file cannot be used here.”
  • A file over its limit is refused with “That file is too large.” The website stops reading as soon as the limit is passed, even when the sender does not say how big the file is.
  • Every file is read through one address, /api/assets/<id>, which checks your organization and then hands the browser a link to the stored file that expires after five minutes. Another organization gets “That was not found.”
  • A raw photo is stored but never handed back. Only the ink lifted from it will be, from step 21.

To try it on your computer, after git pull and pnpm install, add these three lines to apps/web/.env.local:

GCS_ASSETS_BUCKET=ink-studio-assets
GOOGLE_CLOUD_PROJECT=ink-studio-local
STORAGE_EMULATOR_HOST=http://localhost:4443

Then start the storage stand-in, apply the new table, and start the website:

docker compose up -d
pnpm db:migrate
pnpm dev

docker compose ps now lists gcs next to postgres. The bucket and project lines are required: without them the terminal running pnpm dev reports Invalid environment variables and names the missing one. In a second terminal, upload any PNG as a mask and read it back:

curl -s -X POST 'http://127.0.0.1:3000/api/uploads?purpose=mask' \
  -H 'Origin: http://127.0.0.1:3000' -H 'x-file-name: paper.png' \
  --data-binary @apps/web/public/images/paper.png

It answers with the new file's id, for example {"id":"01a17f61-…"}. Open http://127.0.0.1:3000/api/assets/<that id> in the browser and the paper texture appears. /api/assets/<that id>/status answers {"status":"done","error":null}. The row is in pnpm db:studio under assets, and the file itself is under tools/docker/gcs/ink-studio-assets on disk.

The tests run on throwaway Postgres and Cloud Storage containers in Docker:

pnpm --filter @repo/services test --reporter=verbose
pnpm --filter @repo/integrations test --reporter=verbose

The names read like “HEIC is refused with its own code”, “a body that grows past the limit is refused”, and “another organization's asset is invisible”.

Checked: pnpm lint, pnpm typecheck, and pnpm test, including 18 service and 3 storage tests, and every answer above against the local database and storage.

Done 14. Both worker pools on the Pub/Sub emulator

There is now a worker, apps/worker, that will do the slow jobs: lifting ink from photos, building fonts, and rendering proofs. It runs as two pools. The render pool takes only proof rendering, which needs Chromium; the standard pool takes everything else. Work reaches them through a Google Pub/Sub topic called jobs. On your computer a Pub/Sub emulator runs in Docker on port 8086, and each pool has its own filtered subscription. No job exists yet, so the pools only listen; step 15 adds the first one.

  • pnpm dev now starts the website and both pools together.
  • A message nobody handles is logged as unknown message type and dropped, so it never loops forever.
  • A job that fails is handed back to Pub/Sub, which delivers it again.

To try it on your computer, after git pull and pnpm install, add two lines to apps/web/.env.local:

PUBSUB_EMULATOR_HOST=127.0.0.1:8086
PUBSUB_JOBS_TOPIC=jobs

Then give the worker its own settings, start the emulator, and start everything:

cp apps/worker/.env.example apps/worker/.env
docker compose up -d --wait
pnpm dev

The first docker compose up builds the emulator image, about 1.1 GB, so it takes a few minutes once. docker compose ps then lists pubsub as healthy next to postgres and gcs. In the pnpm dev output, look for worker listening twice, once with "pool":"standard" and once with "pool":"render". A MetadataLookupWarning at start is harmless; the emulator needs no Google credentials.

The tests for the queue run in pnpm test:

pnpm --filter @repo/services test --reporter=verbose

The names read like “a message whose processor throws is nacked and logged” and “two processors for one type are refused”.

Checked: pnpm lint, pnpm typecheck, and pnpm test, including 7 queue tests. Both pools ran against the emulator, and a test message for each pool reached only that pool.
